# P26 · C10 Tile 内多阵列共享 AM

状态：未开始
对应原方案：§7.2 C10、§2.2（链级 affinity 与 engine 选择）、§4.1（engine 选取规则）、§8.1b Q08
验证层级：F/C/R；2-Tile 隔离为 RTL harness（R）；板级多阵列归 P27/P28，本任务不宣称 B。

## 1 目标与不做

目标：

1. Tile 内多引擎共享 AM 的硬件化验收：2/4 engines 两套可执行配置（`hardware/configs/tile_2engines.yaml`、`tile_4engines.yaml`，拟新增，字段沿 P05 拼写 `arrays_per_tile` 等），allocator 按 live-handle 最少、平局最小 ID 独立选 engine，与 group 无关；affinity 授予后至 slot_free 固定。
2. 共享的是容量与访问：4 group×2 slot 动态利用、跨 engine 的 AmRouter 路由、各 group RMW 独立、drain 公平；同 context 两链独立推进；slot 换代重分配可改变 engine。
3. 无迁移：bound engine 忙时等原 engine（T05）；同 handle 所有 step 始终原 engine（T04）。
4. ">2 live handles per engine"用1/2engine合法配置验证，4/8均衡下不能强造第3handle；板级归P27/P28的2engine配置，不篡改DUT affinity。
5. Q08：2-Tile RTL 隔离 harness——Tile0 满槽/fault 不影响 Tile1；不扩大到多 Tile FPGA。
6. 原方案 §6.2 必达公平比较（真实数据，非"不保证更快"结论文本）：①输出驻留不均时共享 AM vs 明确标注的私有分区对照的容量利用；②低冲突 vs 热点 group；③单 context 两槽 vs 多 context 四 engine；④FINAL drain 占 quota 对短任务的影响。私有 AM 仅存在于实验/参考容量模型作对照，不开生产 backend、不恢复 private 架构（总则 §6 禁令不变）。

不做K-step跨engine迁移、**同一C输出链**的多engine split-K、跨Tile AM、生产private AM或新scheduler；同context两条独立输出链并行仍必达，不能误禁。私有分区仅作目标6实验对照。

- 修改 `hardware/boa/src/main/scala/` 的allocator/router/result capture/top与测试，以及配置；Gemmini目录仅提供array执行资源，不承载BOA scheduler/router。validator消费P05配置，不恢复旧语义。

## 4 接口与不变量

- engine 选择：授予时按 (live_handle 数, engine_id) 最小者；与 logical_am/group 无关；授予后 affinity 至 slot_free 不变；忙时等原 engine，不迁移（总则 §3.1）。
- 容量：每 engine 同时至多一个 executing step；单 engine 可服务超过两个 live handle；每 context ≤2 live lease 跨 engine 统计；fresh FIFO 不插队、bundle 预留照旧。
- 不同engine可同时请求同group的不同region，实际服务受该group端口/adder仲裁，不承诺同拍并行写；不同group保留独立并行。互锁按物理地址，drain公平。
- 周期/RTL各自运行，对拍bytes、合法所有权与非时序计数。least-live在相同grant线性化状态下必须选同engine；不同完成周期会改变后续slot/live分布，长负载不要求逐链binding表完全相同。另用相同grant/free序列验证确定性选择。
- 观测：trace/PMU 记录每链 bound_engine、每 engine live handles、等待原 engine 的阻塞原因；无隐藏的按 group 绑定。
- §6.2 分解口径：配额/分配（quota、Tile AM full、slot in use、bundle 阻塞区分 fresh FIFO 与 continuation）、申请/唤醒（沿用软件 snapshot/trace 字段名 `request_count`/`parked_count`/`wake_count`/`cancelled_request_count`/`waited_cycles`、reserved_slots、peak_pending）、engine（compute/输入等待/bound-engine 等待分开）、AM group（update 数、port 与 bank/adder 冲突分别计量）、结果（result-credit、O/R、高水位）、输出/链（FINAL_READY、drain 反压、slot-free 延迟、REQ→GRANT、GRANT→FIRST STEP、step 间空洞、FINAL→FREE、总 lease 驻留）；trace 关联 ctx_key/handle/generation/seq/bound_engine/physical group/region，不以笼统 engine_busy 掩盖瓶颈。
- 公平比较前提：对照组与共享组保持 MAC 数、AM 总容量、输入/输出端口带宽、时钟、numeric profile 完全相同；输出阶段带宽按 `E×q×b` 分别核算新 partial、ADD 旧值读、写回，FINAL drain 另计，不算平均流量；不把新增 SRAM/ports 收益记给共享调度。结论必须由真实请求轨迹与 stall 分解支撑。

## 5 实施步骤

1. 2/4-engine 配置实例与 elaboration；硬件 allocator 的多句柄表与 least-live 选择实现（若 P18 已参数化 E 则复用，否则在本任务扩展 top）。
2. AmRouter/ResultCapture 的 E 路数据通路与同 group 仲裁；各 group RMW 独立互锁；drain 公平性实现与计数。
3. 多engine对拍bytes/协议/非时序计数，记录允许的时序分布差异；另用相同grant/free序列逐项核slot/engine选择，不通过强行等待伪造相同周期。
4. 用例集实现（第 6 节全部 case），含 1-engine/2-engine 的 >2 handle 构造（多 context 正常申请，不碰 bound_engine）。
5. Q08 双 Tile harness：RTL 双实例（各自 allocator/AM），交叉注入满槽与 fault，验证隔离与 per-tile 计数。
6. 注册 `multi-array` target cases；板级交接材料（配置/约束输入）提供给 P27/P28，本任务不产 bitstream。
7. §6.2 公平比较 harness（validator 周期/联仿层，拟新增实验模块，不进生产 backend）：私有分区对照模型（同容量静态划分到 chain/engine，标注 `experiment/reference`）；四组对照负载——a) 输出驻留不均（一条长 FINAL drain 链 vs 短链混合，比较槽位利用率与阻塞）；b) 低冲突（链分散 group）vs 热点（多链同 group）；c) 单 context 两槽 vs 两 context 四链（四 engine）；d) 短任务序列（FINAL drain 占 quota 期间新任务申请的等待分解）。每对照保存双方真实请求轨迹（REQ→GRANT、park/wake 时刻）与 §6.2 分解 stall 表。
8. 文档同步：原方案 §7.2 C10 与 §4.1 中"不按 group 绑 engine"的现状表述更新为已验收引用；§6.2 比较结论仅记录实测，不外推 ASIC 性能。

## 6 验收表

| Case ID | 构造 | 必须观测 | 失败特征 |
| --- | --- | --- | --- |
| ma-2eng-baseline | 2-engine 配置冒烟 | bytes 对 oracle；绑定表合法 | 只跑 4-engine |
| ma-4eng-baseline | 4-engine 配置冒烟 | 同上；从空载 least-live 分布可复核 | 绑定按 group |
| ma-1eng-3handles | arrays_per_tile=1，多 context 使单 engine 持 ≥3 live handle | >2 handles 同 engine 服务，按步公平交替（T06） | 改 bound_engine 伪造 |
| ma-2eng-4handles | 2engine、四contexts各两链，共8live handles | 每engine4handles且按step公平服务 | 只有4条总handle却宣称任一engine>2 |
| ma-two-ctx-four-eng | 4-engine，2 context × 2 链从空载起步 | 覆盖 e0..e3，两链互不引入额外依赖（T20） | 引入同 context 假依赖 |
| ma-single-ctx-max2 | 单 context 4 独立输出 | 同时工作 engine ≤2（quota），资源充分时 4-engine 覆盖由两 context case 证 | 单 context 超 quota |
| ma-no-migrate | 某engine被另一已绑定链RUNNING/COMMITTING步骤占用，其他engine空闲 | 待发链仍等原engine；仅FINAL drain背压不足以制造engine忙 | 迁移或错误把drain当engine永久占用 |
| ma-hotspot-fair | 两链同 group + 其他链他 group | 热点 group 吞吐受 bank/adder 上限，等待公平可观测（T11） | 一链饿死 |
| ma-slot-gen-reassign | 换代后重新申请 | 绑定可改变且按当时 least-live 决定；旧代响应不污染（T17） | 绑定残留旧代 |
| ma-q08-two-tile | RTL 双 Tile harness：Tile0 满槽+fault | Tile1 继续推进、计数独立；fault 只影响本 Tile（Q08） | 共享 allocator 状态 |
| cmp-residency | 输出驻留不均负载，共享 vs 同容量私有分区对照（等 MAC/带宽/时钟/profile） | 双方槽位利用率曲线、阻塞分解表、真实请求轨迹；差异可归因到具体 stall 原因 | 只有"不保证更快"文字、无轨迹 |
| cmp-hotspot | 低冲突 vs 热点 group 各一 run | 热点吞吐受 bank/adder 上限的量化等待与公平序证据；低冲突对照同表 | 平均流量口径代替分项带宽 |
| cmp-ctx2-vs-4eng | 单 context 两槽 vs 两 context 四链（四 engine） | 两配置的并发/engine 占用与 lease 驻留对比表，非时序计数均合法 | 拿单 context 满载外推 |
| cmp-final-drain-short | 短任务序列，FINAL drain 期间新申请 | REQ→GRANT 延迟分解含 drain 占 quota 份额；park/wake 计数闭合 | 把等待笼统记为容量不足 |
