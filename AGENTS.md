## Project Overview

This repository has two interlocking deliverables:

1. **ELENOR architecture design docs** (`design/`) — the chip-level specification
   for a future AI accelerator targeting inference and light training. The master
   spec is `design/ELENOR_Architecture_Design_v1.md`; supporting proposals and
   discussion records live under `design/proposal/` and `design/discussion/`.
   **Physical SRAM/NoC values, engine tensor arithmetic, silicon UCE counts, and
   binary ABI are not yet frozen** — the docs defer them with `由后续规格冻结`.
2. **`pipeline_validator/`** — a working Python reference implementation of the
   ELENOR runtime/memory contract. Model scale is 1 Group × 4 Tile, executing
   `Graph → Context(root) → Grid → Task → Tile Program → Engine`. This is the
   **current reference implementation, not a future idea**; runnable features and
   preconditions are listed in `examples/README.md`. The validator does **not**
   compute tensor numerics or claim device performance — simulated cycles are
   not silicon timing.

A third subtree, **`hardware/coral_nexus/`**, is a verification workspace that
pins upstream Coral NPU RTL/compiler submodules and runs staged evidence gates
(G0 → G1 → …) with a locked container, offline-rebuild proofs, and
byte-compared generated artifacts.

The accelerator's central thesis is **`Compute != Control != Data Movement`**:
hardware consumes low-level objects (command buffers, descriptors,
TileGroupTasks, Tile Programs), never high-level graphs. Four engines cover the
workload space:

| Engine  | Full name                       | Responsibility                 | Target workloads                                                          |
| ------- | ------------------------------- | ------------------------------ | ------------------------------------------------------------------------- |
| **BOA** | Block Outer-product Accelerator | Dense compute                  | GEMM, Conv, QK, AV, Expert MLP                                            |
| **EVU** | Enhanced Vector Unit (EVU-MT)   | Irregular / vector compute     | Softmax, Norm, RoPE, Activation, Gather/Scatter, tail/mask                |
| **MFE** | Memory Flow Engine              | Data movement / stream shaping | Page Stream, Segment Stream, Sparse Block, Persistent Memory              |
| **USE** | Unified State Engine            | Stateful / control compute     | Scan, recurrence, dynamic-shape assist, token routing, checkpoint/restore |

Target configs scale edge → datacenter: **Edge** (8–16 tiles, LPDDR), **Balanced** (64 tiles, HBM/DDR), **High End** (128 tiles, HBM). These are product proposals pending PPA validation, not the current simulation scale.

## Architecture & Data Flow

### Hardware hierarchy

```text
Host / System SoC
   └─ Host Interface (PCIe/CXL/AXI) ── Runtime Processor (RISC-V/uCtrl) ── Global PMU
        └─ Global Scheduler / Command Queue / Event Fabric
             ├─ Global DMA (2D/strided/copy)
             ├─ Memory Controller (HBM/DDR/LPDDR)
             └─ Collective Engine (reduce/broadcast)
                  └─ NoC / Router ── Tile Group × N
                       └─ Compute Tile × 8 (per group)
                            ├─ Tile UCE (control)
                            ├─ L1 SRAM + Tile DMA
                            ├─ BOA cluster (OPA × 4)
                            ├─ EVU
                            ├─ MFE tile port
                            ├─ USE
                            └─ local event / PMU
```

- **OPA** (Outer-product Primitive Array) is the BOA's smallest dense-compute primitive — _not_ a runtime-schedulable engine. Tile UCE launches a BOA descriptor; the BOA sequencer lowers it into OPA micro-loops.
- **Tile UCE** (Unified Control Engine) and **USE** are two functional components that may share one tile-local RISC-V / micro-controller. UCE owns program control, engine launch, event wait, stream token, descriptor patch; USE owns state register/cache, scan, recurrence, checkpoint/restore.

### Control-flow hierarchy: `CPU → DevicePort → GroupPort → per-root Sequencer + shared GroupScheduler → Tile → Engine`

```text
CPU nexus.program: submit / depends_on / await; pending / outstanding / completion
  → DevicePort message → GroupPort bounded pending root metadata → full L2/slot/control resource admission
  → per-root TileGroupSequencer: registration cursor + fence + completion
  → Group shared GroupScheduler: bounded action table, poll completion/control → ISSUE → REGISTER
  → bounded Grid Route registration → per-Tile independent Task commit
  → per-Tile Tile UCE: eligible-head RR single-instruction issue → bounded engine queues
  → engine/transfer completion → event → Task safe retire → root retire
```

| Control layer | Current owner                                  | Contract                                                                                            |
| ------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| CPU/Device    | `CpuDeviceController` / `DevicePort`           | `nexus.*` control sequence, dependencies, bounded outstanding; does not hold Group L2 Arena         |
| GroupPort     | `GroupPortAdapter`                             | bounded pending metadata separated from full root resource admission                                |
| Group         | `TileGroupSequencer` + shared `GroupScheduler` | per-root registration/completion separated from bounded ready-action ISSUE; Grid Route manages Task |
| Tile          | `ComputeTile` / Tile UCE                       | per-Tile Task/Frame/UCE pin admission, eligible-head RR, single-instruction issue                   |
| State/Engine  | USE / BOA / EVU / MFE                          | state / compute / data movement; engine microarchitecture still per §8–11 target planning           |

> Sourced from master spec §7.1 (`design/ELENOR_Architecture_Design_v1.md` lines 402–418). The key change from
> the older model: there is no single per-Group Sequencer — each root Context gets its own
> `TileGroupSequencer` (registration cursor / fence / completion), while a shared `GroupScheduler`
> handles bounded ready-action ISSUE/REGISTER, and each Tile commits Tasks independently.

### Data-flow hierarchy

`HBM/DDR/LPDDR → L2 (Group SRAM via Group DMA / MFE) → L1 (Tile DMA / MFE tile port) → Engine (BOA/EVU/USE)`, with `Role → Role` flow through Stream Queues and `Tile → Tile` flow through Collective/Broadcast.

### Execution objects & program residency

A compiled package (`model.pkg`) is **not** a graph or an op — it is `graph_schedule.bin` + `group_tasks/` + `tile_programs/` + `descriptors/` + `weights/` + `relocation_table`. Core objects:

| Object          | Granularity        | Role                                                     |
| --------------- | ------------------ | -------------------------------------------------------- |
| Graph Schedule  | whole graph        | group task dependency, context, queue, memory lifetime   |
| TileGroupTask   | Tile Group         | group task, role dispatch, HBM→L2 DMA                    |
| TileRoleBinding | role               | role_id, tile_mask, Tile Program, in/out stream          |
| Tile Program    | Tile               | Tile UCE executes: L2→L1 DMA, BOA/EVU/MFE/USE            |
| Descriptor      | dynamic params     | shape, stride, address, tiling, stream, state, patch     |
| Stream Queue    | inter-role         | producer-consumer, credit, backpressure, EOS/error token |
| Slot Frame      | Tile L1            | L1 memory binding for tile program + descriptor          |
| Program Table   | residency registry | program_id → section metadata / local handle             |
| Event Table     | runtime/group/tile | completion, dependency, fault, timeout                   |

**Residency contract:** compiler never emits `program.load/prefetch/install`; runtime only registers metadata; Tile Group Sequencer guarantees program-ready before dispatch; Tile UCE only consumes a resident local handle. **Cold Launch** = residency miss → implicit fetch/verify/install. **Warm Launch** = program resident → patch descriptor/context/shape only. Correctness is gated by `program_id + version + hash + epoch`.

### Tile-SPMD programming model

One Tile Program template runs on many tiles; per-tile data is distinguished by `tile_id`, `group_id`, descriptor offset, and slot-frame binding (analogous to CUDA SPMD). The compiler emits MLIR-like IR across six non-overlapping dialects:

| Dialect          | Semantics                                                    | Output                  |
| ---------------- | ------------------------------------------------------------ | ----------------------- |
| `elenor.boa`     | dense GEMM/Conv/QK/AV                                        | BOA descriptor template |
| `elenor.evu`     | elementwise, softmax, norm, mask/tail, gather/scatter subset | EVU descriptor template |
| `elenor.mfe`     | Page/Segment Stream, layout/reorder                          | MFE stream descriptor   |
| `elenor.use`     | state, scan, recurrence, checkpoint/restore                  | USE state descriptor    |
| `elenor.runtime` | command, event, barrier, branch_shape, launch_group_task     | command template        |
| `elenor.package` | section, relocation, manifest, kernel binding                | executable package      |

Dialects must not encroach on each other (BOA dialect never expresses event-wait; runtime dialect never expresses matmul tile layout). The validator implements these as xDSL custom dialects in `pipeline_validator/dialects/elenor.py` with three ownership prefixes: `tile.*` (one Task/Tile Program), `nest.*` (one root Context), `nexus.*` (Host/CPU model).

## Development Commands

```bash
# Python 3.11 conda environment (deps: xdsl, pyyaml, pytest)

conda activate elenor-validator

# Full suite (548 tests, parallel by default via pytest-xdist)
python -m pytest pipeline_validator/tests/ -v
```

### Validator — CLI

```bash
# Compile only → review.json + .exec.txt + .compiled.mlir.txt + .target.yaml
python -m pipeline_validator --ir-file path/to/workload.mlir \
  --input-binding Y=0x100000:131072:rw \
  --compile-only --compiled-output artifacts/review.json

# Hermetic replay (independent process, no source file, no compiler import)
python -m pipeline_validator --compiled-file artifacts/review.json \
  --hw-config artifacts/review.target.yaml \
  --input-binding Y=0x100000:131072:rw
```

Common flags: `--group-policy s0|s1|s2`, `--context-mode N`, `--device-context-mode N`,
`--sim-override KEY=VALUE` (incl. `fidelity=full_memory`), `--max-cycles N`,
`--json` / `--report`, `--detailed`, `--trace-json` / `--trace-html` / `--memory-trace`.
Full semantics: `pipeline_validator/README.md`.

## Code Conventions & Common Patterns

### Design doc conventions

The master spec (`design/ELENOR_Architecture_Design_v1.md`) and any ELENOR module
specs follow a **strict, shared 9-section template**:

1. `## 1. 定位、目标和 First Silicon cutline` — positioning, goals, V1 cutline table (must-close vs. deferred)
2. `## 2. 职责、非职责和 ownership` — responsibilities, non-responsibilities, ownership matrix
3. `## 3. 微架构和状态机` — microarchitecture, FSMs (often sub-`###` per state machine)
4. `## 4. 接口、descriptor、寄存器和协议` — interfaces, descriptor/CSR/ABI drafts (`v0` suffix), protocol
5. `## 5. 数据流、控制流和时序路径` — data/control/timing flows
6. `## 6. 配置、PPA、性能模型和 PMU` — config params, PPA, roofline, PMU counters
7. `## 7. RTL/软件实现建议` — RTL/software implementation guidance
8. `## 8. 验证、bring-up 和验收标准` — verification, bring-up order, acceptance criteria
9. `## 9. 风险、取舍和后续细化方向` — risks, tradeoffs, follow-ups

- **Language:** Primary content is Chinese; technical terms (BOA, EVU, descriptor, TileGroupTask, FSM, etc.) stay in English. Keep this mixed style.
- **Unfrozen values:** Any not-yet-decided number/encoding is explicitly marked with one of `由后续规格冻结` / `由 SRAM profile 冻结` / `由 PPA exploration 冻结`. **Never fabricate binary encodings or physical macros** in a spec — defer them with this marker.
- **ABI versioning:** All interface drafts are tagged `v0`. Treat `v0` as draft, not frozen.
- **Descriptor templates:** Use C-style `typedef struct { … } elenor_*_template_v0_example_t;` with a `patch_mask` field declaring which fields runtime/Tile UCE/MFE/USE may patch. Undeclared fields must not be modified at runtime.
- **Ownership tables:** Module boundaries are explicit — each spec lists what it owns, what it does **not** own, and an ownership matrix. When touching a module, respect and update these boundaries; do not silently expand a module's scope.
- **Diagrams:** ASCII art in fenced `text` blocks for structural/pipeline diagrams; PNG images for rendered architecture figures; mermaid is not used.
- **Cross-references:** Specs reference siblings by module name (e.g. "见 `elenor_compute_tile`"). The master doc is the canonical integration point.
- **Workload mapping tables:** Each engine doc's `## 8` / `## 5` sections map concrete workloads (Dense Attention, Paged Attention, MoE, SSM/Mamba/RWKV, multi-model) to engine roles.

### Python conventions (`pipeline_validator/`, `examples/generators/`, `scripts/`, `hardware/coral_nexus/scripts/`)

The Python code follows PEP 8 enforced by **ruff** (configured in `ruff.toml`)
and static type-checking with **mypy**. Both run as pre-commit hooks —
commits are blocked on lint or type errors.

| Aspect        | Setting                                                                | Source                                           |
| ------------- | ---------------------------------------------------------------------- | ------------------------------------------------ |
| Line length   | **108** characters                                                     | `ruff.toml` `line-length`                        |
| Indent        | **2 spaces** (not 4)                                                   | `ruff.toml` `indent-width`                       |
| Quotes        | **double** (`"`)                                                       | `ruff.toml` `[format]`                           |
| Line endings  | **LF**                                                                 | `ruff.toml`                                      |
| Python target | **3.12** (ruff) / **3.11** (conda runtime)                             | `ruff.toml` `target-version` / `environment.yml` |
| Ruff rules    | E, F, W, I, N, UP, B, C4, RUF                                          | `ruff.toml` `[lint]` `select`                    |
| Ruff ignores  | N801, N802, N803, N806, N812, N813, N815, N818, E731, B905, C901, B006 | avoids renaming arch names like `DMA_DESC`       |
| Type checking | **mypy** (zero errors)                                                 | `.pre-commit-config.yaml`                        |
| Auto-format   | ruff `--fix` + prettier                                                | `.pre-commit-config.yaml`                        |

**Do**:

- Use `from __future__ import annotations` at the top of every `.py` file.
- Add `assert self.program is not None` before accessing `self.program.*`
  when the type system sees it as `Optional`.
- Prefix unused unpacked variables with `_`: `_desc_id, _dst, event_id = ins.args`
- Keep imports sorted: ruff's `I` rules auto-sort them.
- Use `# noqa: F401` on public-API imports only referenced in `__all__`.
- Run `conda run -n elenor-validator pre-commit run -a` before committing.
- 优先保证代码易读、易维护：命名清晰、逻辑直白、避免过度抽象。
- 实现新功能时尽量复用项目中已有的函数/工具，避免重复造轮子；先搜索既有实现再动手。
- 同一功能在多处出现时，应剥离成共享函数并在各处调用，消除重复代码。

**Avoid**:

- Don't suppress ruff rules globally without a comment explaining why.
- Don't suppress mypy with `# type: ignore` unless architecturally necessary.
- Don't use 4-space indent — follow the project's 2-space convention.
- Don't run ruff over `hardware/coral_nexus/upstream/` — it reformats pinned
  submodule files. Scope ruff to `scripts/`, `verification/`, and project-owned
  paths only.

### Coral Nexus workspace conventions

- **Generated/byte-compared artifacts** (in `.prettierignore` and pre-commit
  `exclude`): `protocol/generated/*`, `pipeline_validator/cosim/wire.py`,
  `configs/cs1_c*.yaml`, `configs/params.d/coral_cs1.json`,
  `verification/numerics/upstream_probe/*`, `kernel_bootstrap/kernel_measurement.json`,
  `protocol/PROTOCOL_FREEZE.json`. A formatter must never rewrite them — their
  digest is part of the contract. Run `pre-commit run -a` cautiously; if it
  touches pinned files, restore with `git checkout`.
- **Upstream submodules** are pristine and pinned in `env/sources.lock`; never
  edit files under `upstream/`. Apply changes via `patches/series` (single-owner
  enforced by `patches/file_owners.yaml`).
- **Evidence** lives under `out/coral_nexus/<CARD>/attempt-NNN/`; `out/` is
  gitignored and never constitutes an archive by itself.

## Runtime/Tooling Preferences

### For the validator (`pipeline_validator/`)

- **Runtime:** Python 3.11 via conda environment `elenor-validator`.
- **Formatter:** ruff (`ruff.toml` at repo root). `ruff check --fix` auto-fixes
  imports, formatting, and most lint issues. Prettier handles Markdown/JSON/YAML.
- **Type checker:** mypy (zero errors required; run via pre-commit).
- **Package manager:** pip within the conda environment; no `pyproject.toml` yet.

### For the Coral Nexus hardware workspace (`hardware/coral_nexus/`)

- **Container:** one locked build image `coral-nexus-builder:c002` from
  `env/Dockerfile` (base digest + tool versions in `env/image.lock`). Build with
  `cn env build`; verify with `cn env verify`.
- **Jobs run as caller UID/GID;** no docker socket, no `--privileged`, repo
  mounted read-only.
- **Python split:** validator in conda `elenor-validator`; container python is
  distro-managed only.
- **Dispatcher:** `cn.sh` (host) and `cn` (container) read the same
  `scripts/commands.yaml` registry — no shadow list.

### For the design docs

- **No runtime / package manager** needed. Only Docker for PDF export.

## Testing & QA

```bash
conda run -n elenor-validator python -m pytest pipeline_validator/tests/ -v
```

  transfer/cache, profiles) plus end-to-end simulations (built-in workloads,
  transformer prefill/decode multicontext, paged-attention) and CLI/trace audits.
- **All tests must pass** before committing. Run `pre-commit run -a` first,
  then `pytest`.

### Coral Nexus contract & gate tests (`hardware/coral_nexus/`)

```bash
cn unit --suite contracts           # C009–C020 contract validators
cn unit --suite kernel-bootstrap    # bounded bootstrap ELF resource checks
cn unit --suite numeric-bootstrap   # directed BF16 numeric vectors
cn gate --stage G0 --out <dir>      # G0 gate (31 checks, exit 0 = green)
cn gate --stage G1 --out <dir>      # G1 gate (C009–C020, exit 14 = open budgets by design)
```

Contract suites cover: native owner tags (C010), numeric bit semantics (C011),
VME decl ABI (C012), memory ownership (C013), package image (C014), event/reset
(C015), trace windows (C016), protocol codecs (C017), kernel bootstrap (C018),
sourced targets (C019), G1 gate enforcement (C020). Gate failure classes 11–18;
`gates/G1.yaml` mirrors `REQUIRED_G1_CHECKS` held in `verification/gates.py`
(drift is its own exit 18).

### Design doc review

The document review in `review/ELENOR_Document_Review.md` identified:

- **8 P0 blockers** — shared ABI/contract not frozen, all docs still use "`样例`" (example) structures, Tile Program residency path unfrozen, Paged-Attention cross-engine ABI unfrozen, event-wait lacks sequence/generation fields, Fault Record has two incompatible `v0` definitions, BOA split-K semantics unclosed, EVU V1 cutline contradicts acceptance plan, USE checkpoint/event-assist deferred but V1 depends on it.
- **10 cross-document consistency issues** — command-type enum conflicts, event-status encoding conflicts, fault-record struct conflicts, descriptor naming inconsistency, PMU counter naming fragmentation, stall-attribution layer mismatch, address-reference model inconsistency, context-ID width inconsistency, event-ID width inconsistency, Stream Queue semantics unfrozen.

**Guidance for an AI assistant:** when asked to extend or refine the architecture, prioritize **freezing/aligning contracts** (the P0 + consistency items) over adding new features. When editing a spec, keep the shared 9-section template, the `v0` ABI tagging, the `由后续规格冻结` deferral markers, and the ownership/non-ownership boundaries intact. Cross-check any ABI/descriptor change against `review/ELENOR_Document_Review.md` §3–§4 to avoid widening the consistency gaps.

**Ground-truth order for conflicts:** validator CODE > validator docs/tests/yaml > ELENOR design master doc > other design docs. Grep before trusting any version number or "frozen" claim.
